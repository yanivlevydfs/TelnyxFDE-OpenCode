Architecture

Bindings and hops: webhook → HTTP facade, MCP → RPC shared actor

webhook (Python 3.9) → KV client.storage.kvs.keys.* (REST)
webhook (Python 3.9) → actor HTTP facade: POST /actors/{digits}/{method}
mcp-server (TS) → KV env.KV binding (cache + session)
mcp-server (TS) → actor RPC: env.SESSIONS.idFromName(digits)
session-actor (TS) → env.ITINERARIES: flytlv-itineraries (5-object cap)

Three actor classes: CallerSession, MetricsCounter, AuditLog — all hosted by session-actor.

Cloud Storage: one bucket, 5 keys max — 4 itineraries/slot-<n>.html + one audit/latest.json.

Python webhook cannot bind actors → HTTP facade. TypeScript MCP ships no actor code → RPC via SESSIONS.

Bindings and hops matter. The Python webhook can't bind actors, so it reaches the session-actor through an HTTP facade (POST /actors/{digits}/{method} with a Bearer INTERNAL_API_TOKEN). The TypeScript MCP server skips that hop: it binds CallerSession directly through the env.SESSIONS shared-actor binding — no class code shipped by the MCP function; the runtime forwards the call over RPC. KV is REST from the Python webhook (client.storage.kvs.keys.*) and the env.KV binding from the TypeScript MCP. The session-actor service writes one Cloud Storage bucket, flytlv-itineraries, hard-capped at 5 objects: 4 itinerary slots + one audit/latest.json. Three actor classes, all hosted by session-actor: CallerSession, MetricsCounter and AuditLog.
